# Operating a deployment

Day-two guide for a live millwright deployment: where the moving parts are in
AWS, how to inspect and steer runs from the CLI, and what to check when
something misbehaves.

Millwright has not yet been deployed anywhere. Everything below is derived from
the source and the [implementable specification](specs/1-millwright-v1-implementable-specification.md),
not from observed production behaviour — expect to correct it against the first
real deployment. Commands, flags, and resource names are verified against the
code; where a name is generated by CloudFormation and cannot be predicted, this
document says so rather than guessing.

Throughout, `<name>` is the deployment name — the `deploymentName` passed to the
`Millwright` construct, default `millwright`. It namespaces every physical
resource and the SSM config plane, so several deployments can share an
account and region. The CLI targets one deployment via `--deployment <name>`,
`$MILLWRIGHT_DEPLOYMENT`, or auto-discovery when the account+region holds
exactly one.

## Where things live

Start from the manifest. `cdk deploy` self-registers an SSM parameter at
`/millwright/<name>/manifest` carrying the version, effective poll cadence and
retentions, the permissions boundary, and the **real** physical names of the
state table, polling table, artifact bucket, build log group, build project,
config CMK, and event bus. Every consumer reads names from there rather than
reconstructing them; you should too.

```sh
aws ssm get-parameters-by-path --path /millwright --recursive \
  --query 'Parameters[?ends_with(Name, `/manifest`)].Name'
aws ssm get-parameter --name /millwright/<name>/manifest --query Parameter.Value --output text
```

### Deterministic resource names

| Resource | Name |
|---|---|
| State table (DynamoDB) | `<name>-state` |
| Polling table (DynamoDB) | `<name>-polling` |
| Artifact/cache bucket (S3) | `<name>-artifacts-<account>-<region>` |
| CodeBuild project (all jobs and synth) | `<name>-builds` |
| Run executor (Step Functions, Standard) | `<name>-run-executor` |
| Launcher queue (SQS) | `<name>-launcher` |
| Event bus | `<name>-bus` |
| Build log group | `/millwright/<name>/builds` |
| Config CMK alias | `alias/millwright/<name>` |
| Synth Lambda | `<name>-synth` |
| Post-synth Lambda | `<name>-post-synth` |
| Poller IAM role | `<name>-poller` |
| Synth job IAM role | `<name>-synth-job` |
| Job roles | `mw-<slug>-<hash12>-<fg\|ns>`, under IAM path `/millwright/<name>/jobs/` |

One caveat on the bucket: when the deployment name is long enough that
`<name>-artifacts-<account>-<region>` would exceed S3's 63-character limit, the
construct emits a synth warning and lets CloudFormation name the bucket. The
manifest still records the real name.

The remaining Lambdas — poller, launcher, decider, build-events handler,
step-events writer, sweep, reporter, synth-events handler — are **not** given
explicit function names, so CloudFormation generates them
(`<Stack>-<Path><Hash>`). Find them by stack, not by guessing:

```sh
aws cloudformation list-stack-resources --stack-name <your-stack> \
  --query "StackResourceSummaries[?ResourceType=='AWS::Lambda::Function'].[LogicalResourceId,PhysicalResourceId]" \
  --output table
```

Their log groups are the usual `/aws/lambda/<physical-name>`. Each construct
sets a descriptive `description` on its function (`millwright (<name>) decider:
…`, `… launcher`, `… reporter`, and so on), so `aws lambda list-functions` plus
the description is a reliable way to map logical role to physical name.

### Which log group answers which question

| Question | Look at |
|---|---|
| What did this job print? | `/millwright/<name>/builds` — one stream per build. Prefer `millwright logs`. |
| Did synth fail, and why? | Same build log group (the synth job runs on `<name>-builds`), plus the `<workflow> / synth` check on the commit. |
| Is polling happening at all? | Poller Lambda log group; `Millwright/Poller` metrics; `millwright doctor`. |
| Why did a push not produce a run? | Poller logs (was the ref change seen?), then launcher logs (dedupe, trigger match, bootstrap). |
| Why is a run not progressing? | Decider Lambda logs, the `<name>-run-executor` execution history, and build-events handler logs. |
| Why is a check missing or stale on GitHub? | Reporter Lambda logs. |
| Why did a concurrency-grouped run stay QUEUED? | Decider logs, then sweep Lambda logs. |

Poller metrics live in the CloudWatch namespace `Millwright/Poller`, dimension
`Deployment=<name>`. The ones worth a dashboard: `TickDurationMs`,
`ReposPolled`, `RefEventsEmitted`, `TransportFailures`, `QuarantinedRepos`,
`CircuitBreakerOpen`, `HostKeyRotationReconciled`, `HostKeyHardFailures`, and
the tier-2 set (`PrTickDurationMs`, `PrReposPolled`, `PrEventsEmitted`,
`PrNotModified`, `PrApiErrors`, `PrForkEventsDropped`, `PrBackoffSkips`) and
cron set (`CronEntriesEvaluated`, `CronEventsEmitted`, `CronInvalidExpressions`,
`CronErrors`).

Three alarms ship with the deployment:

- `<name>-poller-overlap` — poll ticks are overlapping their cadence
  (invocations throttled by the poller's reserved concurrency of 1).
- `<name>-poller-circuit-breaker` — the quorum circuit breaker is open; SSH
  transport is failing for a quorum of repos and polling has decayed to a canary.
- `<name>-poller-host-key-rotation` — GitHub rotated its SSH host key and the
  poller auto-reconciled after confirming via `/meta`.

None of them are wired to a notification target by the construct; add an alarm
action in your own app if you want to be paged.

### Config plane (SSM, under the deployment CMK)

Only the manifest is CloudFormation-managed. Everything else is written at
runtime by the CLI under operator IAM.

| Parameter | Contents |
|---|---|
| `/millwright/<name>/manifest` | String — deployment manifest |
| `/millwright/<name>/github/app` | SecureString — GitHub App id + private key PEM |
| `/millwright/<name>/github/host-keys` | String — pinned GitHub SSH host keys |
| `/millwright/<name>/repos/<owner>/<repo>/config` | String (JSON) — `secretsAllowedRefs`, `prPolling`, `forkPrPolicy`, `ecrPullRepos` |
| `/millwright/<name>/repos/<owner>/<repo>/deploy-key` | SecureString — read-only Ed25519 deploy key |
| `/millwright/<name>/secrets/<scope>/<secret>` | SecureString — one workflow secret |

Reading a SecureString needs both `ssm:GetParameter*` and `kms:Decrypt` on the
deployment CMK — the two-gate posture. The set of watched repos *is* the set of
`…/repos/*/config` parameters; that is how both the poller and `repo list`
discover repos.

### Bucket layout

```
runs/<repo>/<workflow>/<number>/in/     model.json, source.tar.gz
runs/<repo>/<workflow>/<number>/out/<job>/<artifact>/
cache/<repo>/                           keyed dependency caches
control/shim/                           the step shim delivery
```

Lifecycle rules expire `runs/` at the artifact retention (default: the metadata
retention, 90 days) and `cache/` at the cache retention (default 14 days), and
abort incomplete multipart uploads after 7 days.

## Inspecting runs from the CLI

There is no web UI. The state table is the source of truth and the CLI is the
lens. Runs are named `<workflow>#<number>` (`ci#142`), qualified as
`owner/repo/ci#142` when two watched repos share a workflow name. Where a run
argument is optional, the latest run is the default.

```sh
millwright runs list [--workflow <wf>] [--ref <ref>] [--status <s>] [--limit <n>]
millwright runs show [<run>]
millwright logs [<run>] [-f|--follow] [--job <name>] [--failed] [--full]
```

- `runs list` shows recent runs newest first; `--limit` defaults to 20,
  `--status` takes a run status (`RUNNING`, `FAILED`, …), `--workflow` accepts
  a bare name or `owner/repo/name`, `--ref` accepts short or full ref form.
- `runs show` renders one run's jobs and steps, including job reuse, skip
  reasons, supersession, and abandoned check reporting, with a CloudWatch
  console deep link per job log stream. It also reads local runs: `millwright
  runs show local-3` reads `.millwright/runs/local-3.json` in the current clone.
- `logs` reads the build log group named in the manifest. `-f` tails via polled
  `GetLogEvents` at roughly a 2 s cadence, `--failed` narrows to failed jobs,
  `--full` dumps each stream from the beginning instead of the tail. A job with
  no `logStreamName` recorded yet (never dispatched) has nothing to print.

`millwright doctor` is the whole-chain check, and the first thing to run when
anything looks wrong. It verifies the manifest and the resources it names,
GitHub App credentials including a per-repo pull-request read probe, each
repo's deploy key over SSH, poller health (last tick, circuit-breaker state),
and registry priming; it reports CodeBuild concurrency and IAM role quotas, and
best-effort checks ECR resource policies and the branch rulesets protecting
`secretsAllowedRefs`. Output lines are tagged `[ ok ]`, `[info]`, `[warn]`,
`[FAIL]`; it exits non-zero if any check fails.

Local runs (`local-N`) never appear in `runs list` and never report checks.

## The run and job state model

**Run statuses** — `PENDING` → `QUEUED` → `RUNNING` → terminal.

| Status | Meaning |
|---|---|
| `PENDING` | The run record exists; it has not yet cleared the concurrency gate. |
| `QUEUED` | Held in a concurrency group's pending slot, waiting for the running slot. |
| `RUNNING` | The run executor is looping the decider. |
| `SUCCEEDED` | Terminal. Every job either succeeded or was skipped by its own `skipIf` guard. |
| `FAILED` | Terminal. At least one job is `FAILED` or `TIMED_OUT` — including the run-deadline path. |
| `CANCELLED` | Terminal. Cancellation was requested, or the run was superseded by a newer run in its concurrency group (`reason: superseded`). |

Only the three terminal statuses can be the source of a rerun.

**Job statuses** — `PENDING` → `QUEUED`/`PROVISIONING` → `RUNNING` → terminal.
`QUEUED` and `PROVISIONING` are CodeBuild's own phases; a burst of concurrent
starts can sit in `QUEUED` for 30–40 seconds, which is queueing, not failure.

| Status | Meaning |
|---|---|
| `SUCCEEDED` | Terminal. Its artifacts are in `out/<job>/`. |
| `FAILED` | Terminal. The build failed. |
| `TIMED_OUT` | Terminal. The job hit its own timeout, or the run-level wall-clock deadline expired and the decider landed it. |
| `CANCELLED` | Terminal. Stopped by a cancellation request. |
| `SKIPPED` | Terminal, with a `skipReason`: `upstream_failed` (a dependency terminally did not succeed) or `skip_if` (its own guard). Only `skip_if` skips count as success for the run. |

Step statuses are `RUNNING`, `SUCCEEDED`, `FAILED`, `SKIPPED`; a step only ever
skips via its own `skipIf`.

Two things to internalise before you debug from the table. First, job rows are
a **projection**: `BatchGetBuilds` is authoritative for terminal job state, so a
stale or wrong job row can never flip a failing sibling green. Second, step rows
are written from events the shim emits and are **display-plane only** — read
them for narrative, never as evidence.

Bounded by contract, and worth knowing before you conclude something is stuck:
each job has a total-attempt cap (default 3, model-overridable), and each run
has a wall-clock deadline (default 24 h, overridable up to the 36 h CodeBuild
ceiling) anchored to the *original* run start so carry-over re-executions never
reset the clock. A run that exceeds it dies a managed death: jobs `TIMED_OUT`,
run `FAILED`, checks reported.

## Cancelling and rerunning

```sh
millwright runs cancel <run> [--repo <owner/name>]
millwright runs rerun  <run> [--repo <owner/name>] [--failed]
```

`<run>` is `owner/name#workflow#number`, or `workflow#number` with
`--repo <owner/name>`.

**Cancel** is decider input, not an outside kill. The CLI writes
`cancelRequested` on the run record and best-effort sends the run's Step
Functions task token to wake the decider now; if the token is stale the wake is
swallowed and the decider picks the flag up within a minute (its token wait
times out at 60 s). The decider then `StopBuild`s in-flight builds, marks
non-terminal jobs `CANCELLED`, marks the run `CANCELLED`, and exits cleanly.
Cancelling an already-terminal run is a no-op and says so. `StopExecution` on
the state machine is break-glass only — it bypasses the cleanup entirely.

**Rerun** creates a *new* run with a fresh run number and `rerunOf` pointing at
the source, from the stored job model. What it does **not** re-do:

- **No re-synth.** The source run's `in/` prefix — `model.json` and
  `source.tar.gz` — is prefix-copied into the new run's prefix. Changes to
  `millwright/workflows.ts` since the source run are not picked up; push a new
  commit for that.
- **No re-resolution of the ref.** The new run carries the source run's `repo`,
  `ref`, and `sha` verbatim. Rerunning `main#7` from three weeks ago builds that
  old commit, not today's head.
- **No trigger matching.** The rerun event names the workflow directly.

The source run must be terminal — rerunning a `RUNNING` run is rejected with
"cancel it or wait". Reruns gate through concurrency groups like any other run,
so a rerun can be `QUEUED`, or supersede/be superseded.

`--failed` re-executes only jobs that ended `FAILED`, `TIMED_OUT`, or
`CANCELLED`, plus their `SKIPPED` dependents. For every job that `SUCCEEDED`,
the launcher prefix-copies its `out/<job>/` subtree into the new run and the
decider seeds it terminal `SUCCEEDED` with `reusedFrom` set — visible in
`runs show`. Note the consequence: a reused job's *side effects* are not
repeated, only its recorded outputs are carried over. If nothing in the source
run is rerunnable, `--failed` is rejected with "drop `--failed` to rerun
everything".

Reruns emit onto the deployment's bus under your own AWS credentials with
`source: millwright.cli`; the bus resource policy rejects that source from any
other principal.

## Troubleshooting playbook

Run `millwright doctor` first. Most of what follows is a specific `[FAIL]` or
`[warn]` it already produces.

### Pushes are not triggering runs

1. **Is the repo watched?** `millwright repo list`. The set of watched repos is
   the set of `/millwright/<name>/repos/*/config` parameters; if it is not
   there, `millwright repo add <owner/repo>`.
2. **Is the poller ticking?** `doctor` fails with "no poller tick recorded" if
   it has never run. Check the poller's log group and `ReposPolled` /
   `TickDurationMs` in `Millwright/Poller`.
3. **Is the circuit breaker open, or the repo quarantined?** A quorum of SSH
   transport failures opens the breaker and reduces polling to a decaying
   canary (`CircuitBreakerOpen` = 1, `<name>-poller-circuit-breaker` alarm).
   A single repo failing with "Repository not found" or a key-auth rejection is
   quarantined on its own (`QuarantinedRepos`); that is a deploy-key problem,
   below.
4. **Is the registry primed?** A repo showing polling activity but no
   default-branch registry entry is a hard `doctor` failure, and it names the
   remedy. This is what `repo add` primes with a `bootstrap` event; if it never
   completed, re-run `millwright repo add`, or push once to the default branch.
5. **Did the event dedupe?** Dedupe is content-derived on
   `EVENT#<repo>#<ref>#<sha>#<kind>` with a 30-minute TTL. A force-push that
   *reverts* to a sha already seen in the last 30 minutes coalesces into the
   earlier run. This is a documented, accepted blind spot — push a new commit
   or `millwright dispatch` to force a run.
6. **Did the trigger match?** Launcher logs record `no-match`. Remember that
   branch config changes take effect from that branch's *second* run: a new
   branch's first push matches against the default branch's registry entry.
7. **Fork PRs are off by default.** Fork-authored PRs produce no runs until you
   opt in with `millwright repo update <repo> --fork-prs on`
   (`PrForkEventsDropped` counts them).

Expected latency, for calibration: push → detection is typically 30–90 s and
worst-case around 2 minutes; push → first log line is typically under two
minutes.

### The synth check is failing

The `<workflow> / synth` check is created `in_progress` at run start and fails
with the error in its summary, so a broken `millwright/workflows.ts` is always
visible rather than silent. Its logs are in `/millwright/<name>/builds`.

Reproduce locally before anything else — `millwright synth` loads the entry
point in-process and prints diagnostics to stderr:

```sh
millwright synth --pretty
```

The cloud synth job differs from your machine in ways that cause most of the
remaining failures: it clones at the triggering commit via the deploy key,
installs by lockfile discovery (`package-lock.json` → `npm ci`;
`pnpm-lock.yaml` → `pnpm install --frozen-lockfile`; `yarn.lock` →
`yarn install --frozen-lockfile`; none → `npm install` plus a lint warning), and
runs the control plane's own synth tooling, never the watched repo's. So: a
lockfile out of sync with `package.json` fails `npm ci` in the cloud while a
warm `node_modules` succeeds locally; and a `millwright-workflows` library
version outside the deployment's supported `schemaVersion` fails there. Check
the deployment's `schemaVersion` in the manifest against the repo's dependency.

A bootstrap (synth-only) execution reports the repo-level `millwright / synth`
context instead of a workflow-scoped one; `synth` is a reserved job name.

### Deploy key / SSH auth failure

Symptoms: the repo is quarantined by the poller, `doctor`'s per-repo deploy-key
check fails, or the synth job cannot clone.

```sh
millwright doctor          # exercises each repo's deploy key over SSH
```

- **Key deleted on GitHub.** `repo add` installs the key via the App's
  Administration permission; someone removing it from the repo's Deploy keys
  page breaks polling and synth. There is no rotate subcommand: remove and
  re-add.

  ```sh
  millwright repo remove acme/api
  millwright repo add acme/api --secrets-refs 'main' # re-specify any config flags
  ```

  `repo remove` deletes the config and deploy-key parameters and best-effort
  deletes the GitHub-side key; `repo add` refuses if the config parameter still
  exists, so remove first.
- **Host key mismatch.** The poller verifies GitHub's SSH host key against the
  pins at `/millwright/<name>/github/host-keys`. On a *confirmed* rotation (it
  re-checks GitHub's `/meta`) it auto-reconciles and raises
  `<name>-poller-host-key-rotation`; otherwise it hard-fails, which is the
  intended behaviour under a MITM. After a legitimate rotation, re-pin:

  ```sh
  millwright refresh-host-keys
  ```
- **Missing pins entirely.** `doctor` names the parameter and tells you to run
  `millwright setup`.

### GitHub rate limiting

The App's installation budget is at least 5,000 requests/hour (cap 12,500).
Design estimate: worst case ~3,000/hr of tier-2 PR polling at 50 repos on
1-minute polls, plus roughly 1,500 check calls/day. Tier 1 — the polling that
actually matters — is pure git over SSH with deploy keys and consumes **none**
of it, so rate limiting degrades PR polling and check reporting, never push
detection.

Symptoms and levers:

- `PrApiErrors` and `PrBackoffSkips` rising: tier-2 is backing off with jitter,
  as designed. Reduce pressure by disabling PR polling on repos that do not need
  it (`millwright repo update <repo> --pr-polling false`) or by lengthening
  `pollCadence`.
- Checks lagging: the reporter backs off per item exponentially, 1 minute to a
  15-minute cap, honouring `Retry-After`. It posts the *latest* desired state,
  so an outage replay coalesces into one call per check rather than a storm.
- Authenticated 304s from PR polling (`PrNotModified`) do not count against the
  primary limit — a healthy tier-2 is mostly 304s.

### Jobs stuck or timing out

- **`QUEUED` for tens of seconds** is CodeBuild's own queue under a concurrent-
  start burst. Millwright queues, it does not fail. If it is chronic, check the
  account's CodeBuild concurrency quota — `doctor` reports it.
- **`PROVISIONING` for minutes** is not expected; provisioning measured 2–7 s
  across the v1 compute matrix. Suspect image pulls: a private ECR image needs
  the repo's `ecrPullRepos` config entry, and cross-account pulls additionally
  need an ECR repository resource policy (`doctor` checks both best-effort).
- **`RUNNING` past its timeout**: the decider treats `BatchGetBuilds` as ground
  truth and reconciles at least every 60 s (its task-token wait times out and
  catches back into the decider), so a job row that looks stuck is often just a
  stale projection. Confirm against CodeBuild:

  ```sh
  aws codebuild batch-get-builds --ids <buildId>   # buildId is on the job row
  ```
- **A run that will not end**: the run-level deadline (default 24 h) is enforced
  by the decider and anchored to the original start across carry-over
  executions, so it terminates the run before Step Functions' 25,000-event
  history ceiling can kill the execution unmanaged. If you do not want to wait,
  `millwright runs cancel` is the clean exit.
- **Repeated retries**: the per-job total-attempt cap is 3 by default. `attempts`
  on the job row tells you how many `StartBuild` claims it has consumed.
- **A `QUEUED` run whose group never freed**: the decider clears a group's
  running slot and starts the pending run on completion; the 1-minute sweep
  repairs groups whose running run is terminal but whose slot never cleared. If
  a run sits `QUEUED` for more than a couple of minutes, read the sweep Lambda's
  logs. The sweep repairs slots — it does not resurrect dead executions.

### Secrets not resolving

Secrets are gated at **dispatch**, by the decider, through job-role variant
selection — not at synth time.

1. **Is the secret written?** `millwright secrets set <name> [--scope <scope>]`
   writes `/millwright/<name>/secrets/<scope>/<secret>`; the scope defaults to
   the repo of the cwd's `origin` remote.
2. **Does the ref qualify?** `secretsAllowedRefs` is unset by default, which
   means *no ref receives secrets*. Patterns match the **short** ref name
   (`main`, `release/1.2`), anchored at both ends, with `*` as the only
   metacharacter — and `*` crosses `/`. `main` matches exactly `main`, never
   `mainline`. Set it with `millwright repo update <repo> --secrets-refs
   'main,release/*'`.
3. **Is it a PR run?** PR refs are structurally unmatchable — `refs/pull/N`
   never short-name-matches — so PR runs never receive secrets in v1. This is a
   rule, not an accident; do not try to pattern around it.
4. **Is the name declared?** Jobs see secrets as the declared environment
   variable name. An undeclared secret is simply absent.
5. **Security check, not a failure mode**: an allowlisted ref name is only as
   strong as GitHub's protection of that namespace. `--secrets-refs 'release/*'`
   hands secrets to anyone who can push `release/anything`. `doctor` warns when
   it can read ruleset state and finds no active branch ruleset covering the
   allowlisted patterns.

### Checks not appearing on the commit

- **Wrong expectation of granularity.** One check per job, named
  `<workflow> / <job>`, plus one workflow-scoped `<workflow> / synth` per run.
  Bootstrap (synth-only) executions report the repo-level `millwright / synth`
  context instead. Per-job checks batch-create as `queued` only *after* synth
  succeeds — before that, `<workflow> / synth` is the only context on the
  commit, which is why branch protection should require it.
- **A newer run owns the context.** The rule is: the newest run owns the check.
  A lower-numbered run's write is silently dropped — its jobs still render fully
  in `runs show`, they just do not touch GitHub. If two runs raced, the older
  one going quiet on GitHub is correct behaviour.
- **PAT mode.** `millwright setup --pat` degrades to commit statuses with
  identical context names, so branch protection works the same way. If you
  expected check runs and see statuses, that is why.
- **Reporter backoff or abandonment.** Unconverged check items back off to a
  15-minute cap and, after 7 days, are marked abandoned — which `runs show`
  displays. Reporter Lambda logs carry the GitHub error.
- **Missing permission.** Check reporting needs the App's Checks: write and
  Commit statuses: write; `doctor` calls out credentials that cannot support
  check reporting.
- **Local runs never report checks.** Only cloud runs do.

## Routine maintenance

### Rotating the GitHub App credentials

```sh
millwright setup --force
```

`setup` refuses to overwrite existing credentials without `--force`. It runs the
GitHub App manifest flow and rewrites `/millwright/<name>/github/app`
(SecureString, under the deployment CMK). Installation tokens are minted on
demand and cached in memory per Lambda only — never persisted — so rotation
propagates as warm Lambdas age out, with no cache to purge.

The App PEM is the highest-value secret in the deployment: it carries
Administration: write, so a stolen PEM permits installing an attacker deploy key
on every watched repo. That is why it sits behind the SSM + CMK two-gate
posture, and why `setup --pat` exists as the tighter-scoping alternative.

### Rotating a deploy key

There is no rotate subcommand. Remove and re-add, re-specifying the repo's
config flags (removal deletes the config parameter along with the key):

```sh
millwright repo list                  # capture the repo's current config first
millwright repo remove acme/api
millwright repo add acme/api --secrets-refs 'main' --ecr-repos '<arn>'
millwright doctor
```

`repo add` mints a fresh read-only Ed25519 key, installs it via the App, and
emits a `bootstrap` event to re-prime the registry.

### Re-pinning GitHub host keys

```sh
millwright refresh-host-keys
```

Re-reads GitHub's `/meta` and rewrites the pins. Run it after the
`<name>-poller-host-key-rotation` alarm fires and you have confirmed the
rotation is genuine — the poller will have already auto-reconciled in memory;
this refreshes the SSM pin itself.

### Upgrading the deployment

Upgrades are npm version bumps plus `cdk deploy` — never a git merge of a cloned
template. In your CDK app directory:

```sh
npm install @copperbox/millwright-cdk@latest
npx cdk diff
npx cdk deploy
millwright doctor
```

Then bring the CLI to the same version (`npm install -g
@copperbox/millwright-cli@latest`, or just `npx @copperbox/millwright-cli`).
After deploying, re-read the manifest: `version` and `schemaVersion` are
recorded there, and `schemaVersion` is what governs which
`millwright-workflows` library versions watched repos may use. A bump can
require watched repos to update their dependency; the failure mode if they do
not is a synth failure with the schema check in its summary.

Nothing in the upgrade path resumes in-flight runs specially — the decider
reconciles from table state and `BatchGetBuilds` on every entry, so a deploy
during a run is expected to be survivable. This is a design property, untested
in production; draining first (no `RUNNING` runs in `millwright runs list`) is
the conservative choice.

### Removing a repo

```sh
millwright repo remove acme/api
```

Deletes `/millwright/<name>/repos/<owner>/<repo>/config` and `…/deploy-key`, and
best-effort deletes the deploy key from GitHub — printing the repo's
`settings/keys` URL if it cannot. Polling stops as soon as the config parameter
is gone, since the config plane *is* the watch list.

What it deliberately does **not** remove: workflow secrets under
`/millwright/<name>/secrets/<scope>/…`, the repo's `REG#` registry rows (which
are TTL-exempt), existing run history in the state table, S3 artifacts and
caches, and the repo's job roles. Delete secrets explicitly if the repo is gone
for good; run history and artifacts age out on their retentions.

## Cost and capacity levers

Full line-item analysis, including the idle floor and the scenario table, is in
[AWS cost analysis](aws-cost-analysis.md). The operational summary: dominance is
**CodeBuild compute ≫ CloudWatch Logs ingestion > S3 storage > Step Functions >
polling stack**, so capacity planning reduces almost entirely to build-minutes.

**Poll cadence** (`pollCadence`, default 1 minute). Lengthening it cuts poller
Lambda-seconds and tier-2 API pressure roughly proportionally, and is the
cheapest relief for GitHub rate limiting. The costs: detection latency rises
directly, and **cron granularity degrades to the cadence** — the poll tick *is*
the cron clock, so with a 5-minute cadence a cron entry fires at most once per
tick, for the latest matching minute. The construct warns about this at synth
time. Cadence must be a whole number of minutes, and the poller's Lambda timeout
is set to 2× the cadence, clamped at Lambda's 15-minute ceiling.

**Log verbosity** is the one line item that can rival the compute bill, at
$0.50/GB ingested, and it is controlled by your jobs, not by millwright. Quiet
your build output before you tune anything else. `retention.logs` (default 30
days) controls storage, not ingestion — it must be one of CloudWatch's supported
day counts or the construct throws at synth.

**Build minutes** are the bill. The levers are job-level: right-size compute
type, prefer ARM, use the keyed dependency cache, and keep the per-build-minute
rounding penalty (5–15% at typical job lengths) in mind for very short jobs.
Every run also pays for a synth job of roughly 1–2 minutes.

**Retentions** trade storage for history: `retention.metadata` (default 90 days)
is the state-table TTL and the default for `retention.artifacts`;
`retention.cache` defaults to 14 days. `REG#` registry rows are exempt from the
metadata TTL — they are configuration, not history.

**The ~50-repo poller ceiling** is wall-clock, not dollars. A tick fans out 8–10
parallel SSH sessions and takes roughly 7–8 seconds at 50 repos; the poller runs
at reserved concurrency 1, so a tick that overruns the cadence self-throttles
the next one, which is what `<name>-poller-overlap` alarms on. Watch
`TickDurationMs` against the cadence as your headroom gauge. Two things move the
ceiling in the wrong direction: a repo with thousands of refs (the `ls-refs`
response scales at roughly 65 B/ref, so a 5,000-ref repo adds hundreds of KB per
tick and real DynamoDB I/O for its compressed ref map), and a shorter cadence.
The documented growth path past roughly 100 repos is sharding the schedule by
repo prefix — designed, not built. Before that, lengthening the cadence is the
lever you have.
